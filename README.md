## เริ่มใช้งาน

```bash
pip install -r requirements.txt

# ใส่ API key ลงไฟล์ .env
echo "GEMINI_API_KEY=<คีย์ของคุณ>" > .env

python build_index.py                  # สร้าง index
python main.py "หลักสูตรมีกี่หน่วยกิต"   # ถามผ่าน command line
python webchat/app.py                  # เปิดเว็บแชทที่ localhost:5000
```

`build_index.py` จะข้ามการสร้างใหม่ถ้าเอกสารไม่เปลี่ยน ใช้ `--force` เพื่อบังคับสร้างใหม่

### เปลี่ยน embedding model

```bash
python build_index.py --list-models          # มีอะไรให้เลือก เครื่องรันไหวมั้ย
python build_index.py --model e5-base        # สร้าง index ของอีกโมเดล
python main.py --model e5-base "คำถาม"       # ถามด้วย index นั้น
```

### รันทีละขั้นและเก็บ log

```bash
python run_pipeline.py                       # ขั้น 1-7 ครบ พร้อมจับเวลาและเก็บ log
python run_pipeline.py --steps 3-7 --model e5-base   # ข้ามการแยกข้อความซ้ำ
```

ทุกครั้งที่รันจะได้ transcript เต็มที่ `logs/runs/` และถ้ามีอะไรผิดพลาดจะได้ไฟล์เพิ่ม
ที่ `logs/errors/` — **โฟลเดอร์ `logs/errors/` ว่าง แปลว่ารันสะอาด**

### เปรียบเทียบ

```bash
python evaluation/build_golden_set.py                    # สร้างชุดทดสอบ 128 คำถาม
python benchmarks/bench_embeddings.py --model e5-base    # วัดทีละโมเดล
python benchmarks/bench_embeddings.py --report           # ตารางเทียบทุกตัวที่วัดแล้ว
```

ทุกการทดลองถูกบันทึกลง `logs/EXPERIMENTS.md` โดยอัตโนมัติ — วันที่ ทดลองอะไร
ตั้งค่าอย่างไร ได้ผลเท่าไหร่ ต่อท้ายเรื่อย ๆ ไม่เขียนทับ

## เลือก embedding model ได้ตอนรัน ไม่ต้องแก้โค้ด

Embedding model คือส่วนที่แปลงข้อความเป็นเวกเตอร์ ถ้าเลือกผิดระบบจะค้นไม่เจอตั้งแต่ต้น
ไม่ว่าโมเดลภาษาจะเก่งแค่ไหนก็ช่วยไม่ได้ — จึงต้องเปลี่ยนเพื่อทดลองได้ง่าย

โมเดลถูกเลือกตอนรัน ไม่ใช่ค่าคงที่ในไฟล์ ลำดับความสำคัญคือ

```bash
python build_index.py --model qwen3-0.6b     # 1. ธงบรรทัดคำสั่ง (ชนะเสมอ)
set RAG_EMBED_MODEL=qwen3-0.6b               # 2. ตัวแปรสภาพแวดล้อม
                                             # 3. ค่าเริ่มต้นใน src/model_registry.py
python build_index.py --list-models          # ดูว่ามีอะไรให้เลือกและเครื่องรันไหวมั้ย
```

แต่ละโมเดลมี index แยกโฟลเดอร์ของตัวเองที่ `vector_db/<key>/` จึงสลับกลับไปมาได้ทันที
หลังสร้างครั้งแรก และ index ของสองโมเดลทับกันไม่ได้ หน้าเว็บแชทมี `/api/models`
กับ `/api/model` สำหรับสลับสด ๆ โดยไม่ต้องรีสตาร์ต

`src/model_registry.py` เก็บทุกอย่างที่ต้องรู้ก่อนดาวน์โหลด — ขนาด, มิติ, RAM ที่ต้องใช้
และรูปแบบ prompt ของแต่ละตระกูล ซึ่งไม่ใช่เรื่องเล็ก: E5 และ Qwen3 ถูกเทรนมาแบบ
**asymmetric** คือฝั่งคำถามต้องมี prefix ที่ฝั่งเอกสารไม่มี ถ้าใส่ผิดจะไม่มี error ใด ๆ
แต่คำถามกับเอกสารจะไปอยู่คนละบริเวณของ space และ recall ตกลงเงียบ ๆ

### ผลวัดจริงบนคลังเอกสารนี้

วัดเมื่อ 25 สิงหาคม 2026 บน RTX 5050 Laptop (8 GB) · 3,128 chunks · golden set 128 คำถาม
จากตาราง CLO · วัดแบบ dense อย่างเดียว (ไม่มี BM25 ไม่มีปักหมุด) เพื่อให้ตัวแปรเดียว
ที่เปลี่ยนคือโมเดล

| โมเดล | params | มิติ | โหลด | เข้ารหัส 3,128 chunks | chunks/s | ต่อคำถาม (p50) | Recall@1 | Recall@5 | MRR |
|---|---|---|---|---|---|---|---|---|---|
| **multilingual-e5-base** | 278M | 768 | 11s | **18s** | **170.0** | **12.3 ms** | **72.7%** | **89.1%** | **0.803** |
| bge-m3 *(ค่าเริ่มต้นเดิม)* | 568M | 1024 | 11s | 58s | 53.5 | 25.6 ms | 63.3% | 81.2% | 0.707 |
| PIXIE-Rune-v1.0 | 568M | 1024 | 17s | 56s | 55.5 | 24.9 ms | 62.5% | 79.7% | 0.703 |
| Octen-Embedding-0.6B | 596M | 1024 | 18s | 78s | 40.1 | 87.6 ms | 47.7% | 55.5% | 0.519 |
| embeddinggemma-300m | 308M | 768 | — | — | — | — | ทดสอบไม่ได้ (gated) | | |

แยกตามสำนวนคำถาม ซึ่งเป็นที่ที่ความต่างอยู่จริง

| โมเดล | ถามด้วยชื่อวิชา | ถามด้วยรหัสวิชา |
|---|---|---|
| multilingual-e5-base | 92.2% | **53.1%** |
| bge-m3 | **96.9%** | 29.7% |
| PIXIE-Rune-v1.0 | 90.6% | 34.4% |
| Octen-Embedding-0.6B | 90.6% | **4.7%** |

อ่านจากผลนี้ได้สี่เรื่อง

**โมเดลเล็กที่สุดชนะ และชนะแบบไม่ต้องเถียง** — `multilingual-e5-base` เล็กกว่า bge-m3
สองเท่า เข้ารหัสเร็วกว่า **3.2 เท่า** ตอบคำถามเร็วกว่า 2 เท่า และ Recall@1 สูงกว่า 9.4 จุด
ผลนี้ยืนยันสิ่งที่วัดไว้รอบก่อน (68.8% vs 64.1%) และรอบนี้ห่างกว่าเดิม เพราะรอบนี้ใส่
prefix `query: `/`passage: ` ให้ E5 ถูกต้องตามที่มันถูกเทรนมา

**ขนาดโมเดลไม่ได้แปรผันตรงกับความแม่นยำเลย** — เรียงตาม params จากเล็กไปใหญ่คือ
278M, 568M, 568M, 596M แต่เรียงตาม Recall@1 ได้ลำดับเดียวกันแบบกลับหัว
โมเดลที่ใหญ่ที่สุดในชุดนี้ทำคะแนนต่ำที่สุด

**อันดับบน Thai-MTEB ทำนายผลบนงานนี้ไม่ได้** — Octen-Embedding-0.6B อยู่อันดับ 6 ของ
leaderboard ส่วน multilingual-e5-base ไม่ติดตารางเลย แต่บนคลังนี้ Octen ได้ 47.7%
ขณะที่ e5-base ได้ 72.7% benchmark สาธารณะวัดงานคนละแบบกับที่เราต้องใช้จริง

**คำถามที่มีรหัสวิชายังเป็นจุดอ่อนของทุกโมเดล** — ถามด้วยชื่อวิชาได้ 90-97% ทุกตัว
แต่ถามด้วยรหัสตกเหลือ 4.7-53.1% ที่น่าสนใจคือ Octen ได้แค่ **4.7%** ทั้งที่ถามด้วยชื่อ
ยังได้ 90.6% — ตระกูล Qwen3 ใช้ last-token pooling ร่วมกับ prefix คำสั่งยาว ๆ
ซึ่งดูจะกลบตัวเลข 10 หลักจนหายไปหมด ปัญหานี้แก้ที่ชั้น retrieval ไม่ใช่ที่ตัวโมเดล

### วัดความเร็วจริงของแต่ละโมเดล

ราคาบอกว่าอะไรถูก ไม่ได้บอกว่าอะไรใช้ได้ วัดเมื่อ 25 ส.ค. 2026 ด้วยคำถามจริง 3 ข้อ
× 2 ครั้ง prompt สร้างจาก retrieval จริง (~1,290 token) เรียกแบบ streaming ไม่มี retry
(`python benchmarks/bench_llm_apis.py`)

| โมเดล | สำเร็จ | TTFT เฉลี่ย | TTFT ต่ำ-สูง | รวมเฉลี่ย | tok/s |
|---|---|---|---|---|---|
| **gemini-3.1-flash-lite** | **6/6** | **1.11s** | 0.97-1.23s | **1.21s** | **72.2** |
| gemini-3.5-flash *(ค่าเริ่มต้น)* | 6/6 | 3.86s | 2.46-6.30s | 4.13s | 32.1 |
| gemini-3-flash-preview | 5/6 | 7.26s | 2.79-14.60s | 7.59s | 17.7 |
| gemini-3.6-flash | 5/6 | 30.98s | 3.18-70.59s | 31.33s | 8.0 |
| gemini-3.7-flash | **1/6** | 79.45s | — | 79.46s | 0.4 |

TTFT คือเวลาจนได้ token แรก ซึ่งเป็นสิ่งที่ผู้ใช้หน้าแชทรู้สึกว่า "ระบบได้ยินหรือยัง"
ส่วน tok/s คิดจาก output token หารด้วยเวลาทั้งการเรียก

อ่านได้สามเรื่อง

**gemini-3.1-flash-lite เร็วกว่าตัวอื่นแบบคนละชั้น** — TTFT 1.11s เทียบกับ 3.86s ของ
ค่าเริ่มต้นปัจจุบัน คือ **เร็วกว่า 3.5 เท่า** แถมสำเร็จ 6/6 และความแปรปรวนต่ำมาก
(0.97-1.23s เทียบกับ 2.46-6.30s) ยังเป็นตัวที่ถูกที่สุดในตารางราคาด้วย

**โควตาหมดกับ 503 เป็นปัญหาจริง วัดได้** — `gemini-3.7-flash` สำเร็จแค่ 1 จาก 6 ครั้ง
ที่เหลือเป็น 503 UNAVAILABLE และ ReadTimeout ส่วน `gemini-3.6-flash` มี TTFT
แกว่งตั้งแต่ 3.18s ถึง 70.59s ระบบสำรองโมเดลใน `src/generator.py` ไม่ใช่การกันเหนียว
แต่เป็นสิ่งที่ทำให้ระบบใช้งานได้จริง

**ลำดับ fallback ปัจจุบันเรียงกลับด้าน** — `LLM_FALLBACK_MODELS` ไล่จาก `3.6-flash`
(TTFT 31s, 5/6) → `3.7-flash` (1/6) → ... → `3.1-flash-lite` (TTFT 1.1s, 6/6) ไว้ท้ายสุด
ตามผลวัดควรกลับลำดับ เอาตัวที่เร็วและเสถียรที่สุดขึ้นก่อน — ยังไม่ได้แก้ในโค้ด
เพราะเป็นการเปลี่ยนพฤติกรรมหลักของระบบ ควรตัดสินใจจากผลวัดหลายวัน ไม่ใช่ครั้งเดียว

**ยังเทียบข้ามค่ายไม่ได้** — เครื่องนี้มีแค่ `GEMINI_API_KEY` ตารางราคาข้างบนมาจาก
หน้าเว็บทางการ แต่เวลาตอบกลับของ OpenAI และ Anthropic ต้องมีคีย์ถึงจะวัดได้จริง
`benchmarks/bench_llm_apis.py` ตรวจคีย์ของทั้งสามค่ายอยู่แล้วและรายงานว่าพบตัวไหนบ้าง


**เหตุผลที่เลือก Gemini คือ free tier ไม่ใช่ความสามารถ** ทุกโมเดล Gemini ในตารางใช้งานได้ฟรี
ภายใต้โควตารายวัน ซึ่งทำให้โปรเจกต์นักศึกษาที่ต้องทดสอบซ้ำหลายร้อยครั้งเป็นไปได้โดยไม่มีค่าใช้จ่าย
ถ้าเทียบเฉพาะความสามารถ โมเดลระดับบนของ Anthropic และ OpenAI ทำคะแนนสูงกว่า —
Artificial Analysis จัด Claude Opus 5 ไว้ที่ 63 และ GPT-5.6 Sol ที่ 61 บน Intelligence Index
(ดึงข้อมูลเมื่อ 25 ส.ค. 2026 หน้าเว็บไม่ได้แสดงคะแนนของ Gemini ในส่วนที่ดึงมาได้
จึงไม่นำมาเปรียบเทียบตรงนี้)

สำหรับงานนี้ความสามารถระดับ Flash เพียงพอ เพราะโมเดลไม่ได้ต้องคิดวิเคราะห์เอง

## กลยุทธ์การค้นคืน

ระบบใช้สามชั้นซ้อนกัน แต่ละชั้นแก้จุดอ่อนของชั้นก่อนหน้า

**Dense (FAISS)** จับความหมาย ถาม "ขั้นตอนลาป่วย" แล้วเจอ "การลากิจส่วนตัว" ได้
แต่มองไม่เห็นรหัสวิชาที่เป็นตัวเลข

**Sparse** จับคำตรงตัว เจอรหัสวิชาได้ แต่ไม่เข้าใจคำพ้องความหมาย

**RRF** รวมสองอันดับเข้าด้วยกันโดยไม่ต้องทำให้คะแนนอยู่สเกลเดียวกัน `score = Σ 1/(60 + rank)`

**ปักหมุดรหัสวิชา** เมื่อพบรูปแบบ `นn-nnn-nnn` ในคำถาม ระบบดึงการ์ดวิชานั้นมาไว้อันดับ 1 โดยตรง

### นอกจาก BM25 มีอะไรอีก — วัดมาแล้ว 6 วิธี

`src/sparse_retrievers.py` มีทางเลือกจากสามตระกูลที่พังคนละแบบ วัดด้วย golden set
ชุดเดียวกัน dense เป็น bge-m3 เหมือนกันหมด เปลี่ยนแค่ฝั่ง sparse
(`python benchmarks/bench_retrievers.py`)

| วิธี | ตระกูล | เดี่ยว ๆ Recall@1 | fuse กับ dense | ถามด้วยรหัส (fuse) |
|---|---|---|---|---|
| **Dirichlet-LM** | query-likelihood | 34.4% | **87.5%** | **81.2%** |
| BM25+ | BM25 variant | 32.8% | 78.1% | 59.4% |
| BM25 *(ที่ใช้อยู่)* | BM25 variant | 32.8% | 77.3% | 59.4% |
| TF-IDF (คำ) | vector space | 9.4% | 68.8% | 60.9% |
| TF-IDF (char 3-5 gram) | vector space | 3.9% | 50.0% | 25.0% |
| BM25L | BM25 variant | 10.2% | 47.7% | 17.2% |
| *(dense อย่างเดียว)* | — | — | 63.3% | 29.7% |

**Dirichlet-LM ชนะ BM25 ขาดลอย 10.2 จุด** และในคำถามที่มีรหัสวิชาชนะถึง 21.8 จุด
เหตุผลอยู่ที่วิธี smoothing: BM25 ให้คะแนนเอกสารที่ขาดคำใดคำหนึ่งไปแบบลงโทษหนัก
ส่วน Dirichlet ถอยไปใช้ความน่าจะเป็นระดับคลัง (`P(t|C)`) แทน เอกสารที่ตรงเกือบหมด
จึงไม่ถูกคัดออก ผลคือ Recall@5 เดี่ยว ๆ ของมันสูงถึง 83.6% เทียบกับ BM25 ที่ 61.7%
— และ RRF ให้รางวัลกับการติดอันดับในทั้งสองลิสต์ ตัวที่ Recall@5 สูงจึง fuse ได้ดีกว่ามาก

**สมมติฐานเรื่อง character n-gram ผิด** — เหตุผลที่ลองคือภาษาไทยไม่มีช่องว่างระหว่างคำ
n-gram ระดับตัวอักษรจึงน่าจะเลี่ยงความผิดพลาดของตัวตัดคำได้ และรหัสวิชา `04-620-201`
น่าจะรอดเป็นชุดตัวอักษรแทนที่จะถูกตัดเป็น `04`/`620`/`201` ผลจริงคือ **แย่ที่สุดในทั้ง 6 วิธี**
(3.9% เดี่ยว ๆ) เพราะ n-gram ของภาษาไทยชนกันมั่วไปหมด เอกสารที่ไม่เกี่ยวข้องเลย
ก็ยังได้คะแนน cosine สูงจาก n-gram ที่พบทั่วไป

**การปักหมุดยังคุ้มอยู่ ไม่ว่าจะใช้ sparse ตัวไหน**

| วิธี | ไม่ปักหมุด | ปักหมุด |
|---|---|---|
| dense+BM25+ | 78.1% | **98.4%** |
| dense+BM25 | 77.3% | 97.7% |
| dense+Dirichlet-LM | 87.5% | 96.9% |

ทุกตัวที่ปักหมุดได้ **ถามด้วยรหัสวิชา 100%** — เพราะการค้นรหัสตรง ๆ ไม่ใช่ปัญหาของ
การจัดอันดับตั้งแต่แรก น่าสังเกตว่าเมื่อปักหมุดแล้ว Dirichlet-LM กลับ**แพ้** BM25+ เล็กน้อย
ข้อได้เปรียบของมันอยู่ที่คำถามซึ่งมีรหัสวิชา ซึ่งการปักหมุดจัดการไปหมดแล้ว

**สรุปสำหรับระบบนี้:** ถ้าเก็บการปักหมุดไว้ ใช้ BM25+ (98.4%) ถ้าไม่มีการปักหมุด
เช่นกับเอกสารประเภทอื่นที่ไม่มีรหัสตายตัว ให้ใช้ Dirichlet-LM (87.5%)
สลับได้ที่ `config.SPARSE_METHOD` หรือ `RAG_SPARSE_METHOD`

### Reranker: มีโค้ดแต่ปิดไว้

Cross-encoder (`bge-reranker-v2-m3`) แก้ปัญหาเดียวกันได้ แต่ใช้เวลา **291 วินาทีต่อคำถาม**
บนเครื่องที่ไม่มี GPU ขณะที่การปักหมุดรหัสวิชาแก้ปัญหาเดียวกันได้ในระดับมิลลิวินาที
`USE_RERANKER` จึงตั้งเป็น `False` เปิดใช้ได้ด้วย `python pipeline/complete_retrieval.py --rerank`

หมายเหตุ: ตัวเลข 291 วินาทีนั้นวัดบน CPU ตอนนี้โปรเจกต์มี `.venv-gpu` แล้ว ควรวัดใหม่บน GPU
ก่อนตัดสินใจว่าจะเปิดถาวรหรือไม่

### ปัญหาที่พบในข้อมูลจริง

**อักขระไทยเพี้ยนจากฟอนต์เก่า** — PDF บางไฟล์ฝังฟอนต์ที่ map สระและวรรณยุกต์ไปยัง
Private Use Area ทำให้ `ข้าพเจ้า` ถูกดึงออกมาเป็น `ข<U+F70B>าพเจ<U+F70B>า` คือวรรณยุกต์กลายเป็น
อักขระที่ไม่มีความหมาย ทั้ง embedding และ BM25 จึงมองไม่เห็น อาการนี้สังเกตยากเพราะข้อความ
ยัง "ดูเหมือน" ภาษาไทยตอนพิมพ์ออกมา

`src/thai_normalize.py` แปลงกลับเป็น Unicode จริงก่อนเข้า pipeline พร้อมซ่อมกรณี `ำ`
ถูกแยกเป็นช่องว่าง (`ค าสั่ง` → `คำสั่ง`) ซึ่งพบ 538 จุดในคลังข้อมูล

**ตาราง CLO ต้องมี parser เฉพาะ** — `CLOs-Computer_Engineering-RMUTT.pdf` เป็นตารางเมทริกซ์
23 หน้า การดึงข้อความแบบปกติทำให้เหลือ chunk ที่มีเนื้อหาเพียง `✓` หลายร้อยอัน
`src/clo_parser.py` ประกอบความสัมพันธ์กลับจากพิกัดคำ แล้วเขียนเป็นประโยค
หนึ่งวิชาต่อหนึ่ง chunk

หมายเหตุ: ไม่ได้ใช้ `page.find_tables()` ของ PyMuPDF เพราะมันประกอบสระ/วรรณยุกต์ไทยผิด
(ได้ `ความสัมพนั ธ์` แทน `ความสัมพันธ์`) ขณะที่ `get_text("words")` ให้ผลถูกต้อง

**7 ไฟล์ยังใช้ไม่ได้** — 3 ไฟล์เป็นภาพสแกนล้วน อีก 4 ไฟล์ฝังฟอนต์ที่ไม่มีตาราง ToUnicode
ดึงออกมาได้เป็นอักขระควบคุมดิบ ทั้งสองกรณีต้องใช้ OCR ซึ่งยังไม่ได้ทำ
ผลคือหัวข้อสหกิจศึกษายังไม่มีในคลังข้อมูล

## สถานะ

ใช้งานได้แล้ว: pipeline ครบทั้ง 7 ขั้น, hybrid retrieval, เว็บแชท, ระบบสำรองโมเดล,
สลับ embedding model ตอนรัน, golden set + metrics, ชุด benchmark ครบ 3 ด้าน,
ระบบเก็บ log และสมุดบันทึกการทดลอง

ยังไม่ได้ทำ:

- `evaluation/eval_retrieval.py` และ `eval_generation.py` ยังเป็นโครง
  (metrics และ golden set เสร็จแล้ว benchmark ใช้ทั้งสองอย่างอยู่)
- OCR สำหรับไฟล์ที่ดึงข้อความไม่ได้ — รอบนี้เพิ่มการตรวจจับแล้ว ระบบจะเตือน
  ลง `logs/errors/` ว่าไฟล์ไหนดึงข้อความแทบไม่ออก แต่ยังไม่ได้ทำ OCR จริง
- index เอกสารหมวด `forms/`, `regulations/`, `textbook/`
- `embeddinggemma-300m` (อันดับ 2 ของ Thai-MTEB) ยังทดสอบไม่ได้ ต้องมี HF token
- วัด reranker ใหม่บน GPU — ตัวเลข 291 วิ./คำถาม เป็นค่าที่วัดบน CPU
- `query_transform.multi_query` และ `hyde` — เทคนิคเสริม ยังเป็นโครง
