## เลือก embedding model ได้ตอนรัน

Embedding model คือส่วนที่แปลงข้อความเป็นเวกเตอร์ ถ้าเลือกผิดระบบจะค้นไม่เจอตั้งแต่ต้น
โมเดลภาษาเก่งแค่ไหนก็ช่วยไม่ได้ จึงต้องเปลี่ยนเพื่อทดลองได้ง่าย

```bash
python build_index.py --model qwen3-0.6b     # 1. ธงบรรทัดคำสั่ง (ชนะเสมอ)
set RAG_EMBED_MODEL=qwen3-0.6b               # 2. ตัวแปรสภาพแวดล้อม
                                             # 3. DEFAULT_MODEL ใน src/model_registry.py
```

แต่ละโมเดลมี index แยกที่ `vector_db/<key>/` จึงสลับกลับไปมาได้ทันทีหลังสร้างครั้งแรก
และทับกันไม่ได้ หน้าเว็บแชทมี `/api/models` กับ `/api/model` สำหรับสลับสด ๆ ไม่ต้องรีสตาร์ต

`src/model_registry.py` เก็บทุกอย่างที่ต้องรู้ก่อนดาวน์โหลด — ขนาด, มิติ, RAM, และรูปแบบ
prompt ของแต่ละตระกูล ซึ่งสำคัญ: E5 และ Qwen3 เป็นแบบ **asymmetric** ฝั่งคำถามต้องมี prefix
ที่ฝั่งเอกสารไม่มี ใส่ผิดจะไม่มี error แต่ recall ตกลงเงียบ ๆ

## Golden set กับ fingerprint

`data/golden_set.json` จับคู่คำถามกับ chunk ที่ตอบได้จริง โดยระบุเฉลยไว้ **สองแบบ**

```json
{"query_id": 1, "question": "...",
 "relevant_chunk_ids":  ["12"],          // ตำแหน่งวันนี้
 "relevant_chunk_keys": ["a3f1c8..."]}   // sha1 ของ source + text
```

ต้องมีสองแบบเพราะ **chunk_id เป็นตำแหน่ง ไม่ใช่ตัวตน** ตอนเพิ่มเอกสารทะเบียนเข้ามา
เอกสารใหม่เรียงมาก่อนตาราง CLO ทุก chunk หลังจากนั้นถูกนับใหม่ เฉลย `"0"` ที่เคยเป็น
การ์ดวิชากลายเป็นหน้าปกของเอกสารอื่น **ทั้ง 128 คำถามชี้ผิดหมดโดยไม่มี error ใด ๆ** —
metric อ่านได้ 0% เงียบ ๆ และถูกบันทึกว่าเป็นโมเดลที่ค้นไม่เจอ

`evaluation/golden_set.py` จึงผูกเฉลยใหม่จาก key ทุกครั้งที่โหลด และรายงานว่าย้ายไปกี่ข้อ
ถ้า key เองก็หาไม่เจอ แปลว่าเนื้อความ chunk เปลี่ยน (ไม่ใช่แค่เลื่อน) มันจะ **หยุดทันที**
พร้อมบอกให้สร้าง golden set ใหม่ แทนที่จะให้คะแนน 0

`fingerprint()` สรุปคลังทั้งชุดเป็น sha1 เดียว ติดไว้กับผล benchmark ทุกไฟล์ สองการวัด
เทียบกันได้ก็ต่อเมื่อ fingerprint ตรงกัน

## กลยุทธ์การค้นคืน

สามชั้นซ้อนกัน แต่ละชั้นแก้จุดอ่อนของชั้นก่อน

- **Dense (FAISS)** จับความหมาย ถาม "ขั้นตอนลาป่วย" แล้วเจอ "การลากิจส่วนตัว" ได้ แต่มองไม่เห็นตัวเลข
- **Sparse (BM25+)** จับคำตรงตัว เจอรหัสวิชาได้ แต่ไม่เข้าใจคำพ้อง
- **RRF** รวมสองอันดับโดยไม่ต้องปรับสเกลคะแนน `score = Σ 1/(60 + rank)`
- **ปักหมุดรหัสวิชา** พบรูปแบบ `nn-nnn-nnn` ในคำถาม ดึงการ์ดวิชานั้นขึ้นอันดับ 1 ตรง ๆ

### เทียบ sparse 6 วิธี

`src/sparse_retrievers.py` มีทางเลือกจากสามตระกูลที่พังคนละแบบ วัดด้วย golden set ชุดเดียวกัน
dense เป็น e5-base เหมือนกันหมด เปลี่ยนแค่ฝั่ง sparse (fingerprint `30cffcd2a35ff359`)

| วิธี | ตระกูล | สร้าง index | เดี่ยว ๆ R@1 | + dense | **+ dense + ปักหมุด** | ถามด้วยรหัส (ปักหมุด) |
|---|---|---|---|---|---|---|
| **BM25+** *(ที่ใช้อยู่)* | BM25 variant | 1.3s | 27.3% | 87.5% | **96.1%** | 100% |
| BM25 | BM25 variant | 1.8s | 27.3% | 86.7% | 95.3% | 100% |
| Dirichlet-LM | query-likelihood | 1.2s | 21.1% | **90.6%** | 93.0% | 100% |
| TF-IDF (คำ) | vector space | 1.5s | 9.4% | 79.7% | 92.2% | 100% |
| TF-IDF (char 3-5 gram) | vector space | 2.7s | 3.1% | 62.5% | 90.6% | 100% |
| BM25L | BM25 variant | 1.3s | **31.2%** | 53.9% | 88.3% | 100% |
| *(dense อย่างเดียว)* | — | — | — | 72.7% | — | 53.1% |

**คอลัมน์ที่ใช้ตัดสินคือ "+ dense + ปักหมุด"** เพราะ `HybridRetriever.retrieve()` ตั้ง
`pin_exact_codes=True` เป็นค่าเริ่มต้น — นั่นคือของที่รันจริง ตามคอลัมน์นั้น **BM25+ ชนะ**
จึงตั้ง `SPARSE_METHOD = "bm25plus"`

**การจัดอันดับพลิกเมื่อเปิดปักหมุด** — Dirichlet-LM ชนะขาดตอนไม่ปักหมุด (90.6% เทียบ 87.5%)
แต่แพ้เมื่อปัก (93.0% เทียบ 96.1%) เพราะสิ่งที่มันเก่งกว่าคือคำถามที่มีรหัสวิชา ซึ่งการปักหมุด
จัดการได้ 100% อยู่แล้ว พอทับซ้อนกันแล้ว สิ่งที่เหลือให้วัดคือคำถามที่ถามด้วยชื่อ
ซึ่ง BM25+ ทำได้ดีกว่า (92.2% เทียบ 85.9%)

**สมมติฐานเรื่อง character n-gram ผิด** — ที่ลองเพราะภาษาไทยไม่มีช่องว่างระหว่างคำ n-gram
ระดับตัวอักษรน่าจะเลี่ยงความผิดพลาดของตัวตัดคำได้ ผลจริงคือ **แย่ที่สุดใน 6 วิธี** (3.1% เดี่ยว ๆ)
เพราะ n-gram ภาษาไทยชนกันมั่ว เอกสารที่ไม่เกี่ยวเลยก็ได้คะแนน cosine สูงจาก n-gram ทั่วไป

**sparse เดี่ยว ๆ หารหัสวิชาไม่เจอเลยสักตัว** — คอลัมน์ "เดี่ยว ๆ" ทุกวิธีได้ R@1 = 0% กับคำถาม
ที่มีรหัส (ยกเว้น BM25L ที่ได้ 1.6%) เพราะตัวตัดคำไทยฉีก `04-620-201` เป็นชิ้นที่ไม่มีความหมาย
นี่คือเหตุผลที่การปักหมุดมีอยู่

### Reranker: มีโค้ดแต่ปิดไว้

Cross-encoder (`bge-reranker-v2-m3`) แก้ปัญหาเดียวกันได้ แต่วัดได้ **291 วินาทีต่อคำถาม**
บน CPU ขณะที่การปักหมุดแก้เรื่องเดียวกันในระดับมิลลิวินาที `USE_RERANKER` จึงเป็น `False`
เปิดได้ด้วย `python pipeline/complete_retrieval.py --rerank`

ตัวเลข 291 วินาทีนั้นวัดบน CPU ตอนนี้มี `.venv-gpu` แล้ว ควรวัดใหม่ก่อนตัดสินใจ

### ความเร็วจริง

ราคาบอกว่าอะไรถูก ไม่ได้บอกว่าอะไรใช้ได้ วัด 25 ส.ค. 2026 ด้วยคำถามจริง 3 ข้อ × 2 ครั้ง
× 2 รอบ prompt จาก retrieval จริง (~1,290 token) streaming ไม่มี retry

| โมเดล | สำเร็จ | TTFT เฉลี่ย | TTFT ต่ำ-สูง | รวมเฉลี่ย |
|---|---|---|---|---|
| **gemini-3.1-flash-lite** | **12/12** | **1.11-3.37s** | 0.97-7.83s | 1.21s |

| gemini-3.7-flash | **4/12** | 75.14-79.46s | 41.76-100.61s | 79.46s |

TTFT คือเวลาจนได้ token แรก ซึ่งเป็นสิ่งที่ผู้ใช้หน้าแชทรู้สึกว่า "ระบบได้ยินหรือยัง"

**โควตาหมดกับ 503 เป็นปัญหาที่วัดได้** — `gemini-3.7-flash` สำเร็จแค่ 4 จาก 12 ครั้ง
ที่เหลือเป็น 503 UNAVAILABLE และ ReadTimeout ส่วน `3.6-flash` มี TTFT แกว่งตั้งแต่ 3.18s
ถึง 70.59s โควตา free tier นับแยกรายโมเดลและรีเซ็ตไม่พร้อมกัน การล็อกโมเดลเดียวจึงพัง
เป็นระยะโดยคาดเดาไม่ได้

`src/generator.py` ไล่โมเดลสำรองเองเมื่อเจอ 429/503 แล้วพักตัวที่หมดไว้ 10 นาที
ในการทดสอบครั้งหนึ่งโควตาหมดไป 3 โมเดลระหว่างตอบ 6 คำถาม แต่ผู้ใช้ไม่เห็นข้อผิดพลาดเลย
**ลำดับสำรองเรียงตามผลวัดข้างบน** ไม่ใช่ตามเลขเวอร์ชัน

**เหตุผลที่เลือก Gemini คือ free tier ไม่ใช่ความสามารถ** — ทุกตัวในตารางใช้ฟรีได้ภายใต้
โควตารายวัน ทำให้โปรเจกต์ที่ต้องทดสอบซ้ำหลายร้อยครั้งเป็นไปได้ ถ้าเทียบเฉพาะความสามารถ
ระดับบนของ Anthropic และ OpenAI สูงกว่า แต่งานนี้โมเดลไม่ได้ต้องคิดวิเคราะห์เอง
หน้าที่คือเรียบเรียงจากข้อความที่ retrieval หามาให้แล้ว งานหนักอยู่ที่ชั้น retrieval

ยังเทียบข้ามค่ายไม่ได้ เพราะเครื่องนี้มีแค่ `GEMINI_API_KEY`
(`bench_llm_apis.py` ตรวจคีย์ทั้งสามค่ายและรายงานว่าพบตัวไหน)

## ข้อมูล

`data/` แบ่งเป็นสี่หมวด `config.SOURCE_CATEGORIES` เลือกว่าจะ index หมวดไหน
ปัจจุบันตั้งเป็น `["curriculum"]`

| หมวด | ไฟล์ | เข้า index |
|---|---|---|
| `curriculum/` | 18 | ✅ 2,381 records → **2,202 chunks** |
| `forms/` | 23 | ❌ |
| `regulations/` | 2 | ❌ |
| `textbook/` | 1 | ❌ |

chunk กระจุกอยู่ที่เอกสารไม่กี่ไฟล์ — `หลักสูตร-683.pdf` 991, `หลักสูตร63` 727,
`คู่มือนักศึกษา69` 282, `CLOs` 64 รวมสี่ไฟล์เป็น 93% ที่เหลือคือเอกสารงานทะเบียน
14 ไฟล์ ไฟล์ละ 5-10 chunks

### ปัญหาที่พบในข้อมูลจริง

**อักขระไทยเพี้ยนจากฟอนต์เก่า** — PDF บางไฟล์ฝังฟอนต์ที่ map สระและวรรณยุกต์ไปยัง
Private Use Area ทำให้ `ข้าพเจ้า` ถูกดึงออกมาเป็น `ข<U+F70B>าพเจ<U+F70B>า` ทั้ง embedding
และ BM25 จึงมองไม่เห็น อาการนี้สังเกตยากเพราะข้อความยัง "ดูเหมือน" ภาษาไทยตอนพิมพ์ออกมา
`src/thai_normalize.py` แปลงกลับก่อนเข้า pipeline พร้อมซ่อมกรณี `ำ` ถูกแยกเป็นช่องว่าง
(`ค าสั่ง` → `คำสั่ง`) ซึ่งพบ 538 จุด

**ตาราง CLO ต้องมี parser เฉพาะ** — `CLOs-Computer_Engineering-RMUTT.pdf` เป็นตารางเมทริกซ์
23 หน้า ดึงข้อความแบบปกติแล้วเหลือ chunk ที่มีแต่ `✓` หลายร้อยอัน `src/clo_parser.py`
ประกอบความสัมพันธ์กลับจากพิกัดคำ แล้วเขียนเป็นประโยค หนึ่งวิชาต่อหนึ่ง chunk

ไม่ได้ใช้ `page.find_tables()` ของ PyMuPDF เพราะมันประกอบสระ/วรรณยุกต์ผิด
(ได้ `ความสัมพนั ธ์` แทน `ความสัมพันธ์`) ขณะที่ `get_text("words")` ถูกต้อง

**7 ไฟล์ยังต้องใช้ OCR** — pipeline ตรวจจับและเตือนลง `logs/errors/` เมื่อขนาดไฟล์กับจำนวน
ตัวอักษรไม่สมเหตุสมผล ตัวหนักสุดคือ `Regulations-rules-and-announcements_2026-05-19.pdf`
42 MB แต่ดึงได้ 4,136 ตัวอักษร (37 chunks) — เข้า index แล้วแต่แทบไม่มีเนื้อหา
ยังไม่ได้ทำ OCR จริง

## สถานะ

**ใช้งานได้แล้ว** — pipeline ครบ 7 ขั้น, hybrid retrieval, เว็บแชท, ระบบสำรองโมเดล,
สลับ embedding model ตอนรัน, golden set ที่ผูกกับเนื้อหา + fingerprint, benchmark ครบ 3 ด้าน,
ระบบเก็บ log และสมุดบันทึกการทดลอง

**ยังไม่ได้ทำ**

- golden set ครอบคลุมแค่ตาราง CLO (2.9% ของคลัง) — ยังไม่มีคำถามงานทะเบียน/ระเบียบ
- OCR สำหรับ 7 ไฟล์ที่ดึงข้อความไม่ออก (ตรวจจับและเตือนแล้ว แต่ยังไม่ OCR)
- index หมวด `forms/`, `regulations/`, `textbook/`
- `embeddinggemma-300m` (อันดับ 2 ของ Thai-MTEB) ต้องมี HF token
- วัด reranker ใหม่บน GPU — ตัวเลข 291 วิ./คำถาม เป็นค่าที่วัดบน CPU
- `evaluation/eval_retrieval.py` และ `eval_generation.py` ยังเป็นโครง
  (metrics และ golden set เสร็จแล้ว benchmark ใช้ทั้งสองอยู่)
- `query_transform.multi_query` และ `hyde` ยังเป็นโครง
- ลบ index กำพร้าใน `vector_db/` ที่ไม่มีโค้ดอ่านแล้ว
